AWS Immune System

Automated IAM access key remediation

Problem

A leaked IAM access key keeps working until someone deactivates it. GuardDuty flags a key being used from a known-bad IP, but it doesn't act on the finding. Someone still has to see the alert, work out who owns the key, and turn it off.

[TODO, optional: why you picked this problem.]

What I built

An EventBridge rule catches the finding and passes the key ID to a Lambda function, which finds the owner and deactivates the key. Nobody needs to be on call for it.

  1. GuardDuty finding for an IAM user access key (severity 7 or higher), or an AWS Health CREDENTIALS_EXPOSED event.
  2. EventBridge filters on finding type, severity and break-glass exemptions, then reshapes the event to {access_key_id}.
  3. UpdateAccessKey only works on long-term keys (AKIA…). Temporary ASIA… credentials are rejected at input validation instead of failing later.
    Lambda (Python 3.12, arm64) calls iam:GetAccessKeyLastUsed to find the owner, then iam:UpdateAccessKey to set the key to Inactive.
  4. Failures land in an SQS dead-letter queue. Every action is logged to CloudWatch with 90-day retention.
Reserved concurrency is capped at 2, so a flood of forged findings can't deactivate every key in the account at once.

The function itself is treated as something an attacker could try to abuse:

  • Only two EventBridge rules can invoke it.
  • The role can't touch IAM roles or the root account.
  • CloudTrail history for the key is left intact for the investigation.
